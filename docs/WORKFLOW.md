# Работа четырёх участников

## Первые 15 минут после получения задания

1. Вместе заполните PROJECT.md: MVP, стек, дедлайн и интегратор.
2. Один участник создаёт каркас, зависимости и реальные CI-проверки.
   Остальные уточняют сценарии и контракты, не создавая конкурирующие каркасы.
3. Слейте каркас. Все обновляют main и начинают отдельные задачи.
4. Заранее проверьте push своей ветки с каждого компьютера.

## Задачи и владение

Создайте GitHub Issue по шаблону. Укажите одного владельца (человек + агент),
область файлов, зависимости и критерии готовности. Используйте Assignee,
если доступно; иначе имя владельца в описании. Перед началом проверьте задачи
и открытые PR. Пересечения согласуйте с интегратором.

Статусы в Issue: ready → in progress → review → done; blocked с причиной.
Два одновременных комментария «беру» не блокируют задачу: владельца нужно
согласовать. Не ведите общий файл статусов, который редактируют все четверо.

## Ветка и PR

В своём чистом checkout создайте ветку от origin/main. Пример имени:
`agent/alex/12-login-form` (подставьте свои login, номер Issue и задачу).

```bash
git fetch origin
git switch -c agent/alex/12-login-form origin/main
```

Перед PR:

```bash
git fetch origin
git merge origin/main
git diff --check
```

Выполните проверки приложения из PROJECT.md, закоммитьте результат и отправьте
ветку. Не делайте force push. Конфликты общих контрактов решайте с владельцами.
Откройте PR в main по шаблону. Интегратор проверяет результат и сливает PR;
пока интегратор не назначен, слияние не выполняется.

SSH предоставляет Git-доступ, но не API для Issues/PR. Если MCP недоступен,
создавайте и обновляйте их через браузер. Вход в браузере не авторизует Git.

## Передача

В Issue после существенного шага и перед паузой:

- дата/время, ответственный и статус;
- ветка, коммит и PR;
- сделано, проверено (команды/сценарии), ограничения;
- блокеры и следующий шаг.

Существенные решения сохраняйте в Issue или отдельном документе; не полагайтесь
на чат агента на другом компьютере. Не прикладывайте секреты и полные логи.

## Настройки GitHub

Владелец репозитория настраивает Rulesets/Branch protection для main:
PR вместо прямого push, один approval, закрытые обсуждения, запрет force push
и удаления ветки. Required checks добавляйте после первого успешного запуска.
Доступность защиты приватных репозиториев зависит от тарифа GitHub.

Этот документ НЕ включает серверную защиту. Если она недоступна,
команда соблюдает тот же процесс по договорённости.

## Проверка инструкций агента

На старте попросите каждого агента назвать прочитанные файлы правил и свою
задачу. Codex использует корневой AGENTS.md; Claude Code — импорт в CLAUDE.md;
для Antigravity подготовлено workspace rule в .agents/rules/.
Если версия инструмента не подхватила правило автоматически, явно попросите
прочитать AGENTS.md, docs/PROJECT.md и docs/WORKFLOW.md перед работой.
