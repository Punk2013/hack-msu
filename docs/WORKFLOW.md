# Работа четырёх участников

## Общение перед началом работы

Прочитай [протокол общения](COMMUNICATION.md) и сообщения в
`coordination/messages/`, адресованные тебе или `all`. Проверяй канал перед
задачей, изменением общих файлов и push, а также после каждого этапа работы.
Запросы, блокеры и передачи отправляй отдельными Markdown-сообщениями через main.
Остановленные агенты автоматически не просыпаются; срочные вопросы дублирует человек.

## Старт

1. Вместе заполните PROJECT.md: MVP, стек и дедлайн.
2. Один участник создаёт каркас, зависимости и реальные CI-проверки.
   Остальные уточняют сценарии и контракты, не создавая конкурирующие каркасы.
3. Опубликуйте каркас в main. Все обновляют main и начинают отдельные задачи.

## Задачи и владение

У задачи один владелец (человек + агент). В Issue укажите область файлов,
зависимости и критерии готовности. Перед работой проверьте открытые задачи.
Пересечения файлов согласуйте с участниками; два комментария «беру» не являются
атомарной блокировкой. Общие конфиги и lock-файлы меняет один владелец за раз.

Статусы: ready → in progress → done; blocked с причиной.
Не создавайте общий файл статусов, редактируемый всеми четырьмя.

## Прямая работа в main

Каждый использует собственный checkout. PR и обязательного интегратора нет.
Перед началом, с чистым рабочим деревом:

```bash
git switch main
git fetch origin
git merge --ff-only origin/main
```

Если есть собственные неопубликованные коммиты, вместо сброса ветки объедините
их с origin/main через обычный merge и проверьте результат.

После реализации закоммитьте только файлы своей задачи. Перед каждым push:

```bash
git fetch origin
git merge origin/main
git diff --check origin/main HEAD
# Выполните реальные проверки приложения из PROJECT.md.
git push origin HEAD:main
```

При конфликте остановите последовательность, согласуйте изменения контрактов,
разрешите конфликт и завершите merge. Затем повторите проверки и push.
Если другой участник успел отправить коммит и push отклонён как non-fast-forward,
повторите fetch → merge → проверки → push. Force push запрещён.
При ошибках авторизации или серверных ограничениях сначала выясните причину.

Делайте маленькие завершённые коммиты. После публикации проверьте CI для своего
коммита; при ошибке сообщите команде и исправьте её отдельным коммитом.
CI после push не предотвращает попадание ошибки в main, поэтому локальные
проверки перед публикацией обязательны, когда они доступны.

SSH даёт Git-доступ; Issues при недоступном API можно вести через браузер.
Вход в браузере не авторизует Git.

## Передача

После значимого шага и перед паузой обновите Issue: дата, владелец, статус,
коммит, сделано, проверено, ограничения и следующий шаг.
Не полагайтесь на историю чата на другом компьютере. Не публикуйте секреты.

## Серверные настройки

Процесс не требует PR и approvals. Запрет force push и удаления main полезен,
если доступен на тарифе. Эти документы не изменяют настройки GitHub.

## Проверка инструкций агента

На старте попросите каждого агента назвать прочитанные файлы правил и свою
задачу. Codex использует корневой AGENTS.md; Claude Code — импорт в CLAUDE.md;
для Antigravity подготовлено workspace rule в .agents/rules/.
Если версия инструмента не подхватила правило автоматически, явно попросите
прочитать AGENTS.md, docs/PROJECT.md и docs/WORKFLOW.md перед работой.
