# Работа четырёх участников

## Общение перед началом работы

Прочитай [протокол общения](COMMUNICATION.md) и сообщения в
`messages/` в ветке `coordination`, адресованные тебе или `all`. Проверяй канал перед
задачей, изменением общих файлов и push, а также после каждого этапа работы.
Запросы, блокеры и память отправляй напрямую в coordination без PR.
Код продукта и общие правила меняются через PR в main.
Остановленные агенты автоматически не просыпаются; срочные вопросы дублирует человек.

## Старт

1. Вместе заполните PROJECT.md: MVP, стек и дедлайн.
2. Один участник создаёт каркас, зависимости и реальные CI-проверки.
   Остальные уточняют сценарии и контракты, не создавая конкурирующие каркасы.
3. Слейте PR с каркасом после ревью Claude или Astra. Все обновляют main и начинают отдельные задачи.

## Задачи и владение

У задачи один владелец (человек + агент). В Issue укажите область файлов,
зависимости и критерии готовности. Перед работой проверьте открытые задачи.
Пересечения файлов согласуйте с участниками; два комментария «беру» не являются
атомарной блокировкой. Общие конфиги и lock-файлы меняет один владелец за раз.

Статусы: ready → in progress → review → done; blocked с причиной.
Не создавайте общий файл статусов, редактируемый всеми четырьмя.

## Ветки, PR и ревью

Одна задача — отдельная ветка от актуального origin/main и один PR в main.
Прямой push в main запрещён для всех агентов. Пример (замените имя ветки):

```bash
git fetch origin
git switch -c agent/LOGIN/TASK origin/main
```

Перед PR закоммитьте только файлы задачи, затем:

```bash
git fetch origin
git merge origin/main
git diff --check origin/main HEAD
# Выполните реальные проверки приложения из PROJECT.md.
git push -u origin HEAD
```

Откройте PR через GitHub API или браузер. SSH сам по себе не создаёт PR.
В описании укажите задачу, результат, проверки и ограничения.

### Кто принимает

Claude под учётной записью Punk2013 или Astra проверяет PR и выполняет merge.
Для Astra явно укажите в PR человека/GitHub login, от чьего имени она работает.
Название модели не является GitHub-учётной записью и само по себе не даёт права
на merge. Рецензент должен отличаться от автора PR и иметь нужные права.
Если PR написал Claude, нужен независимый Astra-рецензент, и наоборот.
При отсутствии доступного независимого рецензента оставьте PR открытым.

Рецензент проверяет весь diff, критерии задачи, влияние на общие контракты,
секреты, результаты локальных проверок и CI. Фиксирует модель, GitHub login,
проверенный head SHA, результаты и вердикт в review. При дефектах запрашивает
изменения; после новых коммитов повторно проверяет новый head SHA.

Сливать можно только проверенный актуальный head без нерешённых замечаний
и с успешными применимыми checks. Наличие CI для пробелов не доказывает
работоспособность приложения. Перед merge проверьте, что head не изменился.
После merge подтвердите результат в main и статус связанных задач.
Не включайте обход checks, не делайте force push.

Markdown задаёт процедуру, но не запускает Claude/Astra автоматически:
участник открывает агенту PR и поручает ревью. Автоматический сервис ревью
и его credentials в этом репозитории пока не настроены.

## Передача

После значимого шага и перед паузой обновите Issue: дата, владелец, статус,
ветку/PR/коммит, сделано, проверено, ограничения и следующий шаг.
Не полагайтесь на историю чата на другом компьютере. Не публикуйте секреты.

## Серверные настройки

Рекомендуется защита main: PR, минимум один независимый approval, закрытые
обсуждения, сброс approval после новых коммитов и успешные checks.
Добавляйте обязательные checks после их первого успешного запуска.
Настройки GitHub не меняются от записи этих документов; доступность зависит
от прав и тарифа. Не считайте защиту включённой без проверки сервера.

## Проверка инструкций агента

На старте попросите каждого агента назвать прочитанные файлы правил и свою
задачу. Codex использует корневой AGENTS.md; Claude Code — импорт в CLAUDE.md;
для Antigravity подготовлено workspace rule в .agents/rules/.
Если версия инструмента не подхватила правило автоматически, явно попросите
прочитать AGENTS.md, docs/PROJECT.md и docs/WORKFLOW.md перед работой.
