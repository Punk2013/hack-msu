# 🛡️ PII-Gateway: Защита персональных данных в агентных процессах

> **Мастер-сводка проекта для команды и экспертов хакатона (Hack-MSU 2026)**  
> *Документ объединяет итоги архитектурных дискуссий (Issue #4), согласованные решения из PR #6 и PR #8, а также план распределения ролей (Issues #9–#12).*

---

## 1. Концепция и проблематика (Зачем мы это делаем?)

### Реальная боль пользователя
Разработчики и аналитики хотят использовать автономных ИИ-агентов (Codex, Claude Code, Cursor, Antigravity) для работы с реальными документами: клиентскими базами, выписками, договорами, претензиями.  
Однако прямая передача таких файлов в облачные API (OpenAI, Anthropic) создаёт критические риски:
* **Утечка персональных данных (ПДн)**: ФИО, паспортные данные, номера телефонов, СНИЛС, ИНН, email и адреса уходят на зарубежные сервера.
* **Нарушение законодательства**: регуляторные требования (152-ФЗ в РФ, GDPR в ЕС) запрещают неконтролируемую трансграничную передачу чувствительных данных.
* **Недоверие**: пользователи боятся давать агентам доступ к реальным корпоративным и личным архивам.

### Наше решение
Мы создаём **PII-Gateway** — легковесный локальный прокси-сервер (reverse-proxy), который выступает прозрачным «шлюзом безопасности» между локальным агентом и внешним LLM-провайдером:
1. Агент выполняет свою задачу обычным образом в любимом терминале.
2. При обращении к LLM прокси перехватывает запрос и заменяет все ПДн на безопасные маркеры или согласованные псевдонимы.
3. Облачная модель рассуждает и генерирует результат на **полностью обезличенных данных**.
4. При возврате ответа прокси подставляет оригинальные данные **только в проверенные локальные файлы** через аргументы инструментов.
5. Исходные персональные данные ни на миллисекунду не покидают машину пользователя.

## 2. Наше УТП и отличия от аналогов

Команда провела детальный конкурентный анализ существующих Open-Source решений:

| Проект | Архитектура | Ограничения и почему мы лучше |
| :--- | :--- | :--- |
| **Microsoft Presidio** | Библиотека / сервис детекции | Слабая поддержка русского языка; не умеет склонять замены по падежам; не встроена в агентный цикл tool calls. |
| **DocCloak / PII GUI** | Браузерное / GUI-приложение | Ручная обработка статичных файлов; не работает как drop-in middleware для автономных консольных агентов. |
| **Brikko Studio** | Десктопный агент (fork OpenClaw) | Требует полного отказа от привычных инструментов в пользу их собственной программы; использует грубые метки `<NAME_1>`. |
| **LiteLLM + Presidio** | Корпоративный AI-шлюз | Тяжеловесный стек, отсутствие падежного согласования и контекстной защиты локальных инструментов. |

### Наши 4 ключевых преимущества:
1. **Drop-in прозрачность**: Агент не знает, что работает через фильтр. Достаточно прописать локальный `base_url` в настройках клиента (Claude Code, Codex, Cursor).
2. **Правдоподобная русская морфология**: Псевдонимы склоняются во всех 6 падежах русского языка с сохранением рода (`Ивана Иванова` ↔ `Петра Смирнова`). Модель видит естественный текст и не ломает грамматику.
3. **Двухуровневая защита (Sandbox + Policy)**: Техническая изоляция сети агента на уровне ОС (доступен только порт прокси) + реальное вырезание запрещённых сетевых команд (`curl`, `WebFetch`) из ответа модели.
4. **Доказательный аудит-стенд**: Прозрачный лог с уникальными синтетическими «канарейками», доказывающий нулевую утечку в исходящем интернет-трафике.

## 3. Архитектурный консилиум: идеи, развилки и принятые решения

В ходе глубокой дискуссии в Issue #4 команда рассмотрела ключевые развилки:

### Развилка 1: MCP-плагин vs Локальный API-прокси
* **Идея плагина**: сделать специальный инструмент `read_sanitized` через MCP.
* **Почему отклонили**: Агент читает и редактирует файлы не только через кастомный MCP, но и через встроенные инструменты (`ReadFile`, `Bash`, `FileEdit`). Закрыть все системные каналы агента на уровне плагина невозможно.
* **Принятое решение**: **Локальный API-прокси (MITM)**. Прокси служит абсолютным «бутылочным горлышком» (chokepoint) — весь исходящий в сеть трафик проходит через него, включая системные промпты, историю и результаты вызовов инструментов.

### Развилка 2: Формат замен (Маркеры vs Правдоподобные псевдонимы)
* **Проблема**: Метки вида `[PERSON_1]` просты для обратной замены, но часто сбивают с толку LLM (модель путает род, ставит глаголы в среднем роде или отказывается заполнять документы).
* **Принятое решение**: В архитектуру заложены **оба режима**:
  * `marker` (базовый, детерминированный): `[PERSON_1]`, `[PASSPORT_RU_1]`.
  * `realistic` (инновационный): генерация правдоподобных ФИО того же грамматического рода (`Faker` + `pymorphy3`) с синхронным сохранением таблицы всех 6 падежей для мгновенного детерминированного unmasking'а $O(1)$.
  * Команда проведёт замер качества работы модели на одной и той же задаче в обоих режимах.

### Развилка 3: Утечка через аргументы инструментов
* **Проблема**: Если прокси возвращает реальные данные в аргументы вызова `WebFetch("https://site.com/?q=Иван_Иванов")` или `curl`, данные утекут через сам инструмент.
* **Принятое решение**: Строгая политика инструментов (**Tool Policy**):
  * Аргументы восстанавливаются **только** для безопасных локальных файловых операций (`Read`, `Write`, `Edit`) внутри рабочей директории (с проверкой через `realpath` и запретом symlink'ов наружу).
  * Для сетевых и неизвестных инструментов вызов **полностью удаляется из ответа модели**, а агенту возвращается сообщение о блокировке политикой безопасности (`finish_reason: "stop"`).

### Развилка 4: Обработка неоднозначностей и тёзок
* Одинаковое имя в разных местах текста не объединяется в одну сущность автоматически.
* Если в документе упомянут «Иванов», он связывается с «Иван Иванович Иванов» только если в контексте есть ровно один подходящий кандидат. Иначе создаётся отдельная сущность с пометкой `ambiguous`.
* При восстановлении неизвестные или изменённые моделью токены не угадываются, а возвращаются со статусом `PARTIAL` / `FAILED` и явным списком неразрешённых ссылок.

## 5. План контрольных точек (Milestones & Gates)

Проект разбит на чёткие, измеримые фазы:

1. **Gate 0 (≤ 2 часа)**:
   * Прокси запускается в сквозном режиме (pass-through) на синтетических данных.
   * Проверяется корректность перехвата истории, tool calls и стриминга.
2. **Gate 1 (≤ 6 часов)**:
   * Включается полное маскирование.
   * Проверка сквозного цикла: *чтение файла → маскирование → ответ LLM → восстановление → сохранение локального файла*.
   * Тест на отказ (Fail-Closed): при сбое детектора запрос к LLM блокируется.
   * Тест на блокировку сетевых инструментов.
   * Тест независимого перехвата трафика снаружи песочницы.
3. **Демонстрация на хакатоне**:
   * Реальный автономный агент получает задачу подготовить персонализированные уведомления по базе клиентов в `.txt/.md`.
   * На глазах жюри демонстрируется:
     * Исходный файл с ПДн (ФИО, паспорта, контакты).
     * Дамп запроса в облачную модель (полностью чистая синтетика).
     * Итоговые сгенерированные файлы на диске (исходные данные корректно восстановлены на своих местах).
     * Сетевой аудит-лог с нулевой утечкой тестовых канареек.
