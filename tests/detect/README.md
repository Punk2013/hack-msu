# Детектор: первый рабочий срез #10

Проверено 25.10.2026 на macOS arm64, Python 3.12.14. Общий API:
`from pii_gateway.detect import detect`; `detect(text, Context(project_id))`.
Результат — типы из `core/types.py`, Unicode code points, `[start, end)`.

## Что работает

- EMAIL: обычные адреса, включая plus-addressing и кириллицу.
- PHONE: российские номера `+7`/`8`, пробелы, скобки, дефисы, NBSP;
  десять цифр без префикса только после `телефон`, `тел.` или `phone`.
  Допускаются повторные пробелы, табуляция и тире `–`, `—`, `‑`.
- PASSPORT_RU: формат 4+6 цифр с разделителем, в том числе `00 00\n000001`
  с настоящим переводом строки; слитные десять цифр только после подписи паспорта.
  Поддержаны также разделитель `№` и подписанная форма `серия … номер …`.
  Проверки «действительности» реквизитов не отбрасывают чувствительные кандидаты.
- PERSON: один локальный `Natasha 1.6.0 / NewsNERTagger`, модель обучена на русских
  новостях. Веса поставляются внутри wheel Natasha, движок использует Slovnet/Navec.
  Модель загружается один раз на процесс, вызовы сериализованы блокировкой.

Ошибки загрузки, выполнения и нарушения контракта превращаются в `DetectError`.
Возвращать только найденные regex-совпадения при сбое NER запрещено.
Текст исключения не включает входные данные или сообщение сторонней библиотеки.
`confidence=None`: калиброванной вероятности нет. `grammemes=None`: морфология
и связывание упоминаний не выполняются; повторяющиеся ФИО остаются разными spans.

При пересечении структурированный тип приоритетнее PERSON. Внутри группы выигрывает
длинный span, затем раннее начало, затем EMAIL → PASSPORT_RU → PHONE → PERSON,
затем лексикографический порядок имени детектора. Пересекающийся проигравший span
удаляется целиком. Результат отсортирован и проверен через `check_spans`.

## Воспроизведение

Установка — по PROJECT.md: `python3 -m venv .venv` и `.venv/bin/pip install -e '.[dev]'`.
Сеть нужна для установки пакетов, inference выполняется локально.

```sh
.venv/bin/pytest tests/detect -q
.venv/bin/python tests/detect/evaluate.py
.venv/bin/python tests/detect/evaluate.py tests/detect/fixtures/synthetic_v0.jsonl
.venv/bin/python tests/detect/evaluate.py tests/detect/fixtures/synthetic_v2.jsonl
```

`synthetic_v0.jsonl` — прежние 7 записей / 14 spans из Issue #10.
`synthetic_v1.jsonl` — 23 записи / 29 spans: v0 плюс инициалы, опечатка, строчные
имена, латиница, отрицательные случаи, форматы контактов. Оба набора — синтетика.
Паспорта и телефоны намеренно невалидные, email используют `.test`.
Это development-набор, не отложенный benchmark и не готовое e2e-дело клиента.

`synthetic_v2.jsonl` добавляет семь случаев форматирования и отрицательных примеров:
всего 30 записей / 34 spans. В `metrics_v2.json` PERSON остаётся 9/3/4,
EMAIL — 6/0/0, PHONE — 8/0/0, PASSPORT_RU — 7/0/0. Все пять новых идентификаторов
распознаны точно; прежние ошибки PERSON не скрыты и не исправлены этим изменением.

Метрика — точное совпадение `(start, end, type)`. Неверная граница даёт FP и FN,
даже если имя целиком перекрыто более длинным span. Проверки контракта не требуют
идеальной точности NER: фактические ошибки сохранены в отчёте, а не скрыты xfail.
Отчёт включает SHA-256 набора и не выводит исходный текст.

## Результат и ограничения

Зафиксированный запуск — `metrics_v1.json`:

| Тип | TP / FP / FN | Precision | Recall |
| --- | --- | --- | --- |
| PERSON | 9 / 3 / 4 | 0.750 | 0.692 |
| EMAIL | 6 / 0 / 0 | 1.000 | 1.000 |
| PHONE | 5 / 0 / 0 | 1.000 | 1.000 |
| PASSPORT_RU | 5 / 0 / 0 | 1.000 | 1.000 |

Все 14 spans v0 найдены точно. На v1 Natasha полностью пропускает строчное имя
и `Alice Example`, захватывает подпись перед инициалами и опечаткой, ошибочно считает
`Ромашка` именем в отрицательном примере. Эти пять случаев требуют следующей итерации.
Результат 100% для структурированных типов относится только к маленькому набору.
Не поддержаны все варианты email по RFC, произвольные международные телефоны,
все записи паспортов, OCR и косвенные идентификаторы.

На этом запуске загрузка + первый inference заняли около 226 мс, тёплый вызов
на коротких примерах — медиана 0.33 мс, максимум 0.74 мс. Это не задержка gateway:
длинная история, параллельные запросы, RAM и полный агентный цикл не измерены.

Есть тест инициализации и inference с запрещёнными Python socket API, тесты сбоев
модели и некорректного span. Это проверка компонента; сетевую изоляцию процесса
и нулевую отправку при ошибке должен независимо проверить стенд #12 и gateway #9.
Успешный пустой список означает отсутствие детекций, а не безопасность документа.

## Исправления после собственного ревью

Поиск email на последовательности `!` раньше повторно сканировал каждый суффикс:
8 000 символов занимали около 38 мс, удвоение длины увеличивало время примерно
вчетверо. Теперь regex начинает поиск только на границе допустимого local-part:
на той же машине 8 000 символов — около 0.4 мс, 64 000 — 3.3 мс.
Отдельный процесс проверяет завершение обработки 250 000 символов за 5 секунд;
широкий лимит предназначен для обнаружения регрессии, а не SLA производительности.

Разрешение пересечений проверяет соседей в отсортированном списке через bisect,
вместо сравнения с каждым уже принятым span. Семантика приоритета прежняя,
проверяется набор из 5 000 повторяющихся упоминаний с дубликатами кандидатов.
Вставка в Python list в худшем случае остаётся линейной; общей гарантии O(n log n)
для произвольного набора кандидатов нет.
