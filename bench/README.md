# Linux sandbox и независимый приёмник: Issue #12

Первый рабочий стенд роли 4. Запускается только на синтетических данных.
Gateway, детектор и vault не заменяются этой утилитой: это отдельная граница
доступа агента и приёмник для проверки того, что дошло до upstream.

## Запуск агента

Нужны Linux с разрешёнными unprivileged user/network namespaces, `bubblewrap`
и `/usr/bin/python3` (3.10+ для маленького внутреннего bridge). Сам проект — Python 3.12+.
Gateway запускается **на хосте отдельно**, по PROJECT.md, по умолчанию `127.0.0.1:8787`.

```bash
mkdir -p demo/out
PII_LOCAL_TOKEN=local-demo-token .venv/bin/python -m pii_gateway.sandbox \
  --workspace "$PWD/demo" --write-root "$PWD/demo/out" \
  --gateway-host 127.0.0.1 --gateway-port 8787 \
  --protect "$HOME/.local/share/pii-gateway/vault" \
  --protect /absolute/path/to/gateway.env \
  -- /usr/bin/python3 "$PWD/demo/standalone_agent.py"
```

`standalone_agent.py` — команда выбранного агентного клиента, не файл из этой
поставки. Внутри выставлены `OPENAI_BASE_URL=http://127.0.0.1:8787/v1` и только
локальный `OPENAI_API_KEY`; ключ провайдера и остальные переменные хоста не передаются.
Тот же `PII_LOCAL_TOKEN` должен быть установлен у gateway.

Входной каталог виден по исходному абсолютному пути, только для чтения.
`write-root` — отдельная существующая подпапка внутри него, доступная для записи.
Сохранение путей позволяет gateway и агенту одинаково проверять пути инструментов.
Рабочую папку всего проекта передавать нельзя: она содержит защищённый код gateway.

Системный runtime из `/usr`, `/bin`, `/sbin`, `/lib*` монтируется read-only.
Дополнительные **доверенные runtime-каталоги** можно передать повторяемым
`--runtime-root /absolute/path/to/agent-venv`. Все необходимые интерпретатору
пути должны существовать в sandbox. Например, conda-based venv может требовать
отдельного runtime conda. Runtime с установленным кодом gateway запрещён;
нужен отдельный agent runtime. Сертификаты/конфиги хоста, домашняя папка,
`/run` и host `/tmp` не передаются. Новые настройки клиента надо создавать
в его отдельном HOME внутри sandbox или в явно выбранном входном каталоге.

Все конфиги/секреты gateway, лежащие вне стандартного vault, укажите через
`--protect`. При пересечении с экспортируемым деревом запуск отклоняется.
Host UNIX sockets, FIFO/device files в экспортируемых деревьях запрещены;
hard links во входных документах также запрещены. Symlink на скрытый путь
не открывает его внутри нового корня. Доверенный оператор выбирает каталоги
до запуска; конкурентная подмена деревьев процессами хоста вне модели угроз.

Для текущего `demo_agent` есть `--demo-agent`: launcher копирует только файл
клиента из установленной версии пакета в приватный read-only runtime.
Код gateway/detect/vault туда не попадает. После `--` указывается Python и
аргументы клиента; путь скопированного script launcher подставляет сам:

```bash
PII_LOCAL_TOKEN=local-demo-token .venv/bin/python -m pii_gateway.sandbox \
  --workspace "$PWD/demo" --write-root "$PWD/demo/out" \
  --runtime-root "$PWD/.venv" --demo-agent \
  -- "$PWD/.venv/bin/python" --base-url http://127.0.0.1:8787/v1 \
  --workspace "$PWD/demo" --model synthetic --max-steps 1 'Синтетическая задача'
```

На conda-based системе дополнительно передайте `--runtime-root` базового conda
prefix. Тест установленного клиента использует тот же script, локальный
аутентифицированный gateway и независимый приёмник. Transformer в нём — тестовая
замена, реальная модель и полный цикл инструментов этим тестом не проверяются.

## Как ограничена сеть

Bubblewrap создаёт отдельные user/net/PID/IPC namespaces, сбрасывает capabilities
и окружение. Host network не разделяется с агентом. Внутри namespace маленький
TCP bridge слушает только `127.0.0.1:<local-port>`. Он соединён с единственным
смонтированным UNIX-сокетом. Host relay открывает только фиксированный
`gateway-host:gateway-port` из доверенного launcher; агент не передаёт ему
адрес назначения. Получается один разрешённый маршрут, а не весь localhost.

При отсутствии bubblewrap, запрете namespaces или ошибке bridge запуск
завершается ошибкой. Никакого автоматического запуска агента без изоляции нет.
Gateway остаётся доверенным компонентом: сам sandbox не обезличивает HTTP.
Это не защита от уязвимостей ядра и не изоляция от злонамеренного владельца хоста.

Основание выбора механизма: [bubblewrap](https://github.com/containers/bubblewrap),
[network namespaces](https://man7.org/linux/man-pages/man7/network_namespaces.7.html).

## Приёмник на месте upstream

```bash
.venv/bin/python -m pii_gateway.sandbox.upstream_spy \
  --manifest bench/fixtures/synthetic_canaries.json --port 18999
```

В тестовом gateway задайте `PII_UPSTREAM_BASE_URL=http://127.0.0.1:18999/v1`.
Приёмник принимает только обычный JSON `POST /v1/chat/completions`, не проксирует
запросы в интернет и отвечает фиксированным синтетическим текстом. Streaming,
chunked request bodies и API discovery здесь не реализованы.

После Ctrl+C печатает число запросов, их общий размер, число запросов с канарейками
и ID найденных канареек. Тела запросов, значения заголовков и ключи не сохраняются.
В памяти остаются не более 1000 последних записей с ID/счётчиками; общий отчёт
учитывает все запросы за запуск.
Манифесты без `synthetic: true` отклоняются. Отсутствие запросов — не успешный
результат masking: обычный тест обязан увидеть запрос; тест fail-closed — ноль.
Положительный контроль намеренно отправляет исходную синтетику и обязан обнаружиться.

Проверяются заданные значения и варианты в UTF-8, строках JSON (включая `\u`)
и URL percent encoding. Произвольное кодирование, шифрование и неизвестные PII
этот конечный список канареек не обнаруживает. Ноль совпадений не доказывает
отсутствие любых утечек. Это наблюдение на принимающей границе до TLS, независимое
от audit log gateway; пакетный захват на Arch демо здесь не заявляется выполненным.

## Воспроизводимые проверки

```bash
.venv/bin/python -m pytest tests/sandbox -v -rs
.venv/bin/python -m ruff check src/pii_gateway/sandbox tests/sandbox
```

Реальный namespace-тест сначала проверяет доступность bubblewrap. Если ядро или
CI запрещает namespaces, он помечается **SKIP с причиной**, не подтверждает
изоляцию и не позволяет объявить gate пройденным. На машине демо этот тест
должен пройти без SKIP. В ограниченной среде Codex нужен разрешённый запуск
тестов вне её sandbox; иначе NETLINK_ROUTE может быть запрещён самой средой.

Проверяемые свойства:

- разрешённый gateway принимает запрос, другой host listener доступен положительному
  контролю снаружи, но недоступен дочернему процессу агента;
- vault, WAL/SHM, конфиг и исходники gateway скрыты; чтение оригиналов через
  абсолютный путь и symlink отклоняется, попытки записи не меняют файлы хоста;
  вход read-only, export writable; отдельные HOME и /tmp остаются временными;
- агент не получает ключи/окружение хоста;
- отдельный HTTP receiver видит masking, ловит намеренный bypass, не получает
  запросов при инъекции ошибки фильтра или неизвестном вложении.

В boundary-тестах detector/vault заменены явным synthetic transformer. Это проверка
границы gateway/spy, не метрики реального NER или полного пользовательского агента.
Финальный запуск на Arch и с выбранным клиентом остаётся интеграционной проверкой #9/#12.
